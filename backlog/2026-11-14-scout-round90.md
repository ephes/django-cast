## Operational limits

The lock covers cooperating publishers sharing host, user and temp directory;
it is deliberately coarse across keys. It cannot protect against direct target
writes, different hosts or isolated temp directories. Such writers must be
quiesced. Generic Storage has no conditional final write. Existing-file final
save failure remains backend-dependent; process-kill recovery remains manual.
Hash budgets check around synchronous calls, not inside blocked backend I/O.
These limits and recovery steps are documented in `docs/operations/backup.rst`.

Only the repository clone is changed. The existing consumer configurations were
read under `~/projects/homepage/config/settings/` and
`~/projects/python-podcast/config/settings/`; no consumer files were written.
Their production caches use FileBasedCache, whose add operation does not provide
atomic admission. **Before rollout, the owner must choose a supported shared
Redis/Memcached backend for these consumers** (or explicitly disable the posting
limit). Keeping file cache with the enabled limit intentionally refuses posts.
Deploy comment workers together; old workers cannot share the new slot budget.
The consumer backup uses FileSystemStorage without overwrite enabled: existing
refresh refusal is preserved, and refresh still requires overwrite support.
